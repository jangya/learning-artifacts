How does this work?

Start with ordinary deterministic JavaScript: parameters go into layout() and out come six rectangles. Handwired does not parse this source automatically: we explicitly record the same arithmetic with its Circuit builder. It represents compatible computation with neural-network-like weighted sums and ReLU-gated products. There is no dataset, pretrained model, LLM, or service call.

The forward pass still computes the deterministic program. The loss is also inside the circuit. Seeding its derivative with 1 lets backpropagateReference() calculate how each adjustable input affects it. Projected gradient descent changes those four inputs, then renders the circuit's new geometry.

parameters → layout → geometry → loss
desired UI properties → loss → gradients → better parameters

The discrete boundary: a column count is not differentiable. Ordinary JavaScript enumerates 1, 2, and 3 columns; each candidate holds its count fixed while Handwired optimizes width, gap, chart height, and padding. The lowest-loss feasible candidate wins (minimum card width: 200 px). A column change can still jump. No gradients through column selection, DOM measurements, text wrapping, or CSS are claimed.

The objective: 100 × squared overflow / viewport² + 100 × pairwise intersection area / 100,000 + wasteWeight × (0.25 × unused row width / viewport + squared unused row width / viewport² + (gap / 100)²) + 0.002 × mean squared geometry movement / 100,000 + ((width − preferredWidth) / preferredWidth)² + 0.8 × ((chartHeight − preferredChart) / 100)² + 0.3 × ((padding − preferredPadding) / 20)² + 0.6 × ((gap − preferredGap) / 20)². The Space efficiency slider controls wasteWeight; selecting a preset restores its weight. Manual edits keep the other preferences and mark the objective Custom. Waste readout is the actual empty fraction of the card region; the loss uses the simpler differentiable surrogate above. Positive gaps make overlap zero by construction; its penalty is retained and measured, but is inactive in this version.

Movement references are frozen at the start of each solve. Bounds keep parameters readable; a feasibility projection keeps a row inside its viewport after each update. Backtracking evaluates the same objective and rejects uphill steps. Every 60 ms, one step per candidate is attempted, with width/gap and chart/padding in separate descent blocks so an edge constraint cannot stall content sizing. At a fixed width the best loss is non-increasing, but a new viewport or objective changes the function and may raise it. FP32 derivatives treat rounding as real arithmetic; ReLU's slope is zero at its corner.

A real step through the program:

Why Handwired? It supplies the recorded forward computation and its real reverse-mode derivatives. Plain JavaScript alone does not supply those derivatives. For a production dashboard, CSS Grid is simpler, handles intrinsic content and accessibility better, and needs no iterative solver. This is an inverse-problem teaching experiment, not AI generating a UI.
